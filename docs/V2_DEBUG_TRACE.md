# V2 Debug / Trace 学习页

在 V2 项目目录设置 `PROCUREMENT_DEBUG=true` 后启动 Streamlit。PowerShell 示例：

```powershell
$env:PROCUREMENT_DEBUG="true"
.\.venv\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1
```

重新提交一次请求，页面将记录并展示本次运行的 11 个阶段：原始请求、意图输入/输出、业务上下文、候选池、特征转换、决策输入/输出、Optimizer、Validator/Repair、最终结果。先用 High Traffic + Budget 1000 场景阅读一次完整流程，再切换其他场景。

每个阶段展示执行者、实际快照、状态及已采集的耗时，支持 SKU 检索与 JSON 导出。Provider 标记的 `actual_provider_request` 是 SDK 调用边界的参数快照；其他模型输入记录是调用层的契约数据。模型响应不代表可验证的内部思考过程。缺失记录会标记“未采集”，不能解释为该步骤执行成功。业务数据表中的来源与筛选范围说明应一起阅读；相关上下文不等于每条记录都参与了每次计算。

Trace 仅驻留当前 Streamlit 会话，刷新展示不重跑模型；新请求开始新记录。启用前的历史运行没有完整快照。价格、库存等本地证据单独采集，不添加到模型 Payload。认证字段与常见凭证形式在快照及导出时脱敏。该视图包含内部业务数据，应仅在本地或受控开发环境启用；URL 参数不能绕过环境开关。


## 第一次怎么读

输入 `For Cafe Store 001, high traffic is expected next week. Budget is NZD 1000.`，然后按以下顺序检查实际结果（示例不是预设答案）：

1. 核对实际解析的门店与业务日期，再看意图里的预算和客流是否匹配原文；区分模型原始输出与本地标准化结果。
2. 在候选池中挑一个入池商品和一个被排除商品，先确认两者是否都曾交给模型。
3. 查看所选 SKU 的原始订单、库存、指标和阈值，再对照 Safe Signals。缺数据而产生 UNKNOWN 也属于需要理解的结果。
4. 展开 `actual_provider_request`，确认决策模型实际看到的是哪份上下文；对照模型返回的优先级、强度和信号。
5. 在本地优化步骤逐项读取需求基线、库存缺口、强度系数、销售步长、供货限制和预算变化；最终数量由这段计算产生。
6. 阅读每轮校验及修复，再核对最终去向。正常不采购、模型未选、约束无法分配、执行失败和 V1 降级需要分别判断。

记下“预期 / 实际 / 对应事件序号 / 问题所属模块”。模型解释是待核对的输出，真正可验证的依据是请求、数据、计算与校验记录。
